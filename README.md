# dark-ipfs storage node

This repository runs exactly one production storage pair per server:

```text
Kubo + IPFS Cluster peer
```

Every server uses the same Compose file. Multiple servers join one global CRDT
Cluster over the private network. Store API is not part of this stack; it uses
the endpoint pool generated by the deployer.

For the single-machine `developer` profile, each pair also joins the external
`dark-net` network under an installer-generated unique alias. Developer HA runs
this Compose project twice with different node environment files, ports,
identities and volumes. This lets the co-located Store API use both peers while
administrative host ports remain bound to loopback. Developer aliases are
runtime-only; production endpoints derive from topology node addresses.

## Generated configuration

`dark-deployer` generates `.env.node` for a single pair or one
`.env.node.<node-id>` file per Developer HA peer. It includes:

- the logical node name;
- the server's private/VPN address (production only);
- bootstrap addresses derived from the shared node list;
- the global Cluster name and replication factors;
- absolute paths to the Kubo swarm key and Cluster secret.

The secret files are mounted read-only. `.env.node`, persistent identities and
data volumes are never committed. The first peer in the topology seeds a new
Cluster; every other peer discovers a running peer's persistent identity through
its private API and joins it.

## Logging

The deployer passes `GOLOG_LOG_LEVEL` to both Kubo and IPFS Cluster. Production
uses `warning` by default; set `settings.ipfs.logging.level` to `DEBUG` in a
local or diagnostic inventory to include detailed daemon logs. The entrypoint's
startup messages remain intentionally concise.

The entrypoint applies Kubo's `autoconf-off` profile on every start and disables
anonymous telemetry. Private swarms use only their explicitly configured
bootstrap peers and do not inherit discovery, routing, publishing or AutoTLS
endpoints from the public IPFS mainnet.

Required VPN connectivity:

| Port | Purpose |
| ---: | --- |
| `4001/tcp+udp` | Kubo swarm |
| `9096/tcp+udp` | Cluster swarm |
| `5001/tcp` | Kubo API, private consumers only |
| `9094/tcp` | Cluster REST, private consumers/operators only |
| `9095/tcp` | Cluster Proxy, private operators only |

## Operations

```bash
make validate     # render and validate Compose configuration
make up           # start this Kubo/Cluster pair
make ps           # show container state
make logs         # follow logs
make identity     # print persistent Kubo and Cluster identities
make smoke-test   # add, pin and retrieve through this pair
make down         # stop containers and preserve volumes
```

For Developer HA, select a peer explicitly:

```bash
make identity ENV_FILE=.env.node.developer-storage-1
make down ENV_FILE=.env.node.developer-storage-1
make up ENV_FILE=.env.node.developer-storage-1
```

There is deliberately no automated volume-reset command. Removing the named
Kubo or Cluster volumes destroys a node identity and its local copy of content.

Global audits and allocation repair run from `dark-deployer`:

```bash
python3 install.py storage audit
python3 install.py storage reconcile
```

## Persistent repositories after a peer outage

Kubo and Cluster entrypoints initialize identities and wait for bootstrap APIs only for a new repository. On restart, an existing repository starts its daemon using stored peer routes and state, even when all configured bootstrap APIs are unavailable. Kubo preserves its existing bootstrap list instead of clearing it on every restart. This lets a surviving node serve recovery data independently.

The bootstrap endpoint environment variables are used for initial discovery; reconcile stored peer routes explicitly when hosts change addresses. API management addresses and advertised P2P addresses may differ. Preserve identities, swarm/Cluster secrets and CRDT state while updating routes. Greenfield seed behavior remains supported.


Run the entrypoint regression tests without Docker or network access:

```sh
python3 -m unittest discover -s tests -p 'test_*entrypoint_restart.py'
```

These tests exercise persistent startup with unavailable bootstrap APIs, preservation of saved routes, and initial discovery for new seed and non-seed repositories. The Cluster tests mock Linux-only in-place configuration edits on macOS; they verify startup ordering rather than listener configuration. The restart behavior was also exercised with real Kubo and Cluster containers in the isolated AWS backup lab.
